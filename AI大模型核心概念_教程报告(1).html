🧠 概念总览

这篇教程讲什么、适合谁读、以及最省力的读法。

一句话介绍

把 AI 行业的「黑话」翻译成人话。你现在天天听说大模型、智能体、知识库、MCP……听着一堆新名词，其实背后只有一套逻辑。这篇教程沿着一条主线——聊天 → 查资料 → 调工具 → 自主干活 → 安全可控——把 12 个概念串成一个故事，读完你就能听懂 AI 产品发布会在讲什么。

🧱 基础层：模型怎么理解你说的话

这一层的 6 个概念不负责干活，只负责一件事：听懂人、记住事。这是一切能力的地基。

1. LLM · 大语言模型 Large Language Model

定义核心引擎。它把文字拆成 token，然后预测下一个最该接什么。

你玩过词语接龙吗？我说「今天天气真——」，你脱口而出「好」。LLM 就是把接龙玩到极致的机器：它在海量人类文字上训练过，接龙接得又快又像样。

注意一个关键点：它的本质是预测下一个词，不是真的「懂」。但预测得足够准，看起来就像什么都懂了——这就是你能跟它聊天的全部秘密。

2. Token · 文字的最小积木

定义模型理解文字的最小单元，每个 token 对应一个数字 ID。

模型不认识「字」，更不认识「词」，它只认识 token。把一句话想成乐高作品：先拆成小块，每块编个号，模型眼里的世界就是这一串编号。

示意# 一句话进入模型前，会先被拆成 token、再变成数字 「我爱吃火锅」 → 拆块：我 / 爱 / 吃 / 火锅 → 编号：[1230, 4521, 88, 3246] #（数字为示意）
为什么你在乎 token？因为计费按 token、长度限制按 token。中文一个字大约对应 1~2 个 token，一段话多少 token，直接决定花多少钱、能塞多少内容。

3. Prompt · 提示词 你对模型说的话

定义你发给模型的每一段文字，都是 prompt。

prompt 就是「点单」。同一个厨师（模型），你说「来点吃的」，和你说「微辣牛肉面、不要香菜、面煮硬一点」，端上来的东西天差地别。模型没变，变的是你说的话。

4. Prompt Engineering · 提示词工程 把话说清楚的方法论

定义问得越好，答得越好。它研究的就是怎么把话说清楚。

听起来高深，其实全是常识：给背景、提明确要求、举例子、让它一步步想。同一件事，两种问法对比：

❌ 模糊问法帮我写个周报
✅ 会问的我是销售。这周做了三件事： 1. 签下 A 客户（合同额 20 万） 2. 回访了 8 家老客户 3. 搭好了报价模板 帮我写成周报，分「本周进展 / 数据 / 下周计划」三段， 语气专业，200 字以内。

同一个模型，第二种问法的答案一定更好——这就是 Prompt Engineering 的全部：「把话说清楚」。

5. Context · 上下文 每次都带着历史去见模型

定义每次发消息时，系统都会把历史对话打包，整个发给模型。

一个冷知识：模型本身是「金鱼记忆」，每次对话都当你是第一次见面。你感觉它记得前面聊了什么，是因为聊天软件每次都把之前的对话复印一份，连同你的新消息一起塞给它。

你发第 10 条消息时，模型实际收到的是：第 1 轮问答 + 第 2 轮问答 + …… + 你的新消息。一整包，每次都是。

6. Memory · 记忆 记不住，就压缩着记

定义上下文窗口有限，模型把旧对话压缩成关键信息保存。

「打包历史」有个致命问题：包裹越塞越满。上下文窗口（一次能塞给模型的最大 token 数）是有限的，聊到几百轮，最早的内容就塞不进去了。

于是系统学我们做笔记：把旧对话压缩成几条关键信息——你叫什么、在做什么项目、有什么偏好——新对话开始时，把笔记本递给模型。这就是「记忆」。

一句话分清：Context 是「随身带着的完整聊天记录」，Memory 是「记性不够用时的压缩笔记」。
走到这里，模型已经能听懂人话、记住聊过什么了。但它只知道训练数据里的公共知识——你公司的制度、你的私有资料，它一概不知。怎么办？下一层登场。

⚙️ 能力层：模型怎么真正干活

基础层只解决「听懂」，这一层的 6 个概念解决「办事」：查资料、调工具、独立干活、安全可控。

7. RAG · 检索增强生成 Retrieval-Augmented Generation

定义让模型能读你的私有资料：切片存进知识库，提问时检索相关片段，拼进上下文再生成回复。

大白话：RAG 就是让模型从「闭卷考试」变成「开卷考试」。它不用背下你的全部资料，答题时现场翻书就行。翻书分三步：

  1. 切片入库把你的文档（合同、手册、聊天记录）切成小段，存进知识库。就像把一整本书拆成一页一页的卡片。
  2. 按题检索你提问时，系统先拿着问题去库里翻卡片，找出最相关的几段。
  3. 拼接作答把这几段塞进上下文，让模型照着它们回答——答案有出处，还不容易瞎编。
为什么不把所有资料直接塞给它？一是窗口塞不下，二是按 token 计费、全塞又贵又慢还容易跑题。所以只检索最相关的几段——这就是 RAG 存在的理由。

8. Function Calling · 函数调用 模型开口下指令

定义让模型能调用外部工具：模型输出结构化的调用指令，程序执行后把结果还给模型。

反直觉的一点：模型自己不会查天气、不会下单、不会算复杂数字。它能做的是「说」——输出一张格式工整的「工单」，真正干活的是外部程序：

json{ "name": "get_weather", "arguments": { "city": "北京", "date": "今天" } }

程序拿到工单，去查真实天气，把结果递回给模型，模型再组织成人话答复你。一句话：模型是动嘴的，程序是动手的。

9. MCP · 模型上下文协议 Model Context Protocol

定义统一所有第三方工具接口的协议。

有了 Function Calling，模型会「下工单」了。但新问题来了：每接一个工具，就要写一遍对接代码，工具一多乱成一团——就像每个电器的插头形状都不一样。

MCP 把插头统一成同一个标准：工具方按 MCP 规范提供能力，AI 应用按 MCP 规范来取用，两边即插即用。想在 AI 应用里挂一个「文件读写」工具，配置文件长这样：

json{ "mcpServers": { "filesystem": { "command": "npx", "args": ["-y", "@modelcontextprotocol/server-filesystem", "/path/to/folder"] } } }
最容易搞混的点：MCP 不是 Function Calling 的替代品。Function Calling 管「模型怎么输出指令」，MCP 管「工具怎么被统一接入」——一个在模型侧，一个在工具侧，是配合关系。

10. Agent · 智能体 从回答问题到独立办事

定义把 LLM + 规划 + 工具调用 + 记忆打包成能独立干活的系统：接到目标后自己规划步骤、调用工具、记录结果。

前面讲的模型，都还是「你问一句、它答一句」。Agent 是给了目标就放手：「帮我调研三家竞品的价格，做成对比表。」它自己拆步骤（先列竞品 → 再逐个查 → 再汇总），自己调工具（搜索、浏览器、表格），自己记中间结果，最后交作业。

对应关系很好记：LLM 是大脑，规划是流程，工具是手脚，记忆是工作日志——合起来就是一个数字员工。

11. Skill · 技能 给 Agent 的规则手册

定义可复用的结构化偏好和规则文件，Agent 接到类似任务时自动参考。

它和 prompt 的区别：prompt 是一次性便签，skill 是一本可以反复翻的规则书。你不会每次点外卖都重新解释一遍「少辣少糖」——把偏好写进 skill，Agent 每次接到同类任务，自动翻出来照着做。

markdown · SKILL.md 示意--- name: weekly-report description: 写周报的固定偏好 --- - 用「进展 / 数据 / 计划」三段式 - 语气专业，不堆形容词 - 数据必须给同比

12. Harness · 马具 套在 Agent 身上的缰绳

定义给 Agent 套上的「马具」：划定边界红线、自动验收成果、引导修复，确保 Agent 可控。

Agent 能自己干活了，新问题也来了：它会不会跑偏？会不会误删文件？别一觉醒来，发现它把你电脑格式化了。

Harness 就是给野马套上的马具，三件套：

  • 缰绳（红线）：哪些事坚决不许做，提前划死；
  • 验收（考官）：干完自动检查成果合不合格；
  • 修复（回炉）：不合格就打回，引导它自己修到合格为止。
记住这个分工：Agent 负责「能干」，Harness 负责「可控」。没有 Harness 的 Agent，能力越大越危险。

🔗 最容易混的四组概念

这四组概念面试常考、聊天常混。各用一句话切开，外加一组容易混淆的近邻。

概念对 一句话区分 关系
Function Calling
vs MCP		 Function Calling：模型怎么输出指令（模型侧）；
MCP：工具怎么被统一接入（工具侧）。		 配合，不是替代。一个管下工单，一个管统一插座。
Prompt
vs Skill		 Prompt 是一次性便签，说一次用一次；
Skill 是反复翻的规则书，同类任务自动复用。		 口头交代 vs 书面制度。
Context
vs Memory		 Context 是本次随身携带的完整聊天记录；
Memory 是窗口装不下时压缩保存的笔记。		 Memory 是 Context 的搬运工和压缩包。
RAG
vs Context		 RAG 是「去图书馆找书」的动作；
找回来的书，还是要拼进 Context 里才用得上。		 RAG 是给 Context 补料的手段。
判断技巧：遇到两个概念打架，先问「它们各在哪一侧」——模型侧还是工具侧、一次性还是可复用、本次还是长期。位置对了，关系就清楚了。

🧬 一条主线串起所有概念

把 12 个概念放回时间线：每一个，都是被上一个阶段的具体问题逼出来的解决方案。

  1. 第 1 站 · 聊天（LLM / Token / Prompt / Prompt Engineering）先有一台会接龙的大脑。问题来了：它不认识字？——拆成 token。它答得不好？——学会把话说清楚。
  2. 第 2 站 · 记住（Context / Memory）接着发现聊久了它就忘了开头。解法：每次把历史对话打包带上（Context）；包塞不下了，就压缩成笔记（Memory）。
  3. 第 3 站 · 查资料（RAG）然后发现它只懂公共知识，不知道你的私有资料。解法：外接一座图书馆，切片入库、按题检索、拼进上下文——从闭卷变开卷。
  4. 第 4 站 · 调工具（Function Calling / MCP）再发现它只会说不会做。解法：模型输出结构化工单、程序动手干活（Function Calling）；工具接多了太乱，就统一插座标准（MCP）。
  5. 第 5 站 · 自主干活 + 安全可控（Agent / Skill / Harness）最后发现每一步都盯着太累，干脆把大脑、规划、工具、记忆打包成数字员工（Agent）；经验写成规则书让它自动参考（Skill）；再套上马具防止跑偏（Harness）。
整条线的本质：聊天 → 查资料 → 调工具 → 自主干活 → 安全可控。每个概念，都是被上一个阶段的具体问题逼出来的解决方案。以后再遇到新名词，先别慌，问一句：「它是来解决什么问题的？」

❓ 常见问题

新手最常见的 6 个疑问，点开看答案。

MCP 会取代 Function Calling 吗？▼
不会。两者不在同一侧：Function Calling 回答的是「模型怎么把调用意图表达出来」，MCP 回答的是「工具怎么按统一标准被接入」。MCP 接进来的工具，最终还是要靠模型输出调用指令去用。它们是上下游配合，不是竞品关系。
「上下文窗口」到底是什么？对话太长会怎样？▼
窗口就是一次能塞给模型的最大 token 数，相当于背包容量。对话太长、资料太多时，最早的内容会被挤出去——所以模型有时会「忘记」几轮之前说过的话。应对办法就是 Memory（压缩成笔记）和 RAG（资料放外库、用时再检索）。
Token 为什么总是被提起？▼
因为模型世界里的一切「量」都按 token 计：API 计费按 token 数，上下文窗口按 token 数限长，响应速度也和一次处理的 token 量相关。中文大约 1 个字 ≈ 1~2 个 token，估算成本和长度时很有用。
RAG 和「直接把文件发给模型」有什么区别？▼
发文件 = 把整本书塞进背包，占窗口、费 token，文件一大就装不下。RAG = 书放图书馆，每次只把「最相关的几页」取出来放进背包。省空间、省钱、答案还更有针对性。资料少时直接发没问题；资料一多、要用多次，就上 RAG。
Agent 会不会失控？靠什么管住它？▼
会跑偏，所以需要 Harness：红线划死「什么不许做」，自动验收检查「干得对不对」，修复引导让「不合格就回炉」。另外 Skill 也在帮它少犯错——常见任务的正确做法提前写成规则书，它照着做就不容易出格。能力靠 Agent，安全靠 Harness，缺一不可。
一个新任务，我该写 Prompt 还是写 Skill？▼
看复用次数。一次性的临时任务，直接写 prompt，用完就扔；会反复做的同类任务（每周周报、固定格式翻译、固定流程的资料整理），把要求和偏好沉淀成 skill，一次写好、次次生效。判断口诀：说第二遍的时候，就该写 skill 了。
